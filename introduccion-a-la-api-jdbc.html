    3.2. Pasos para manejar una base de datos

    En la arquitectura anterior, el manejo de una base de datos a través del programa de consola implica los siguientes pasos:

    1. cargar el controlador JDBC de la base de datos;
    2. abrir una conexión con la base de datos;
    3. ejecutar una consulta SQL en la base de datos y procesar los resultados de la consulta SQL;
    4. cerrar la conexión;

    El paso 1 se realiza una sola vez. Los pasos 2 a 4 se realizan repetidamente. Tenga en cuenta que las conexiones no se dejan abiertas; se cierran tan pronto como dejan de ser necesarias.

    3.2.1. Paso 1: Carga del controlador JDBC en la memoria

    El código

    
        // driver loading JDBC
        try {
            Class.forName(nom de la classe du pilote JDBC);
        } catch (ClassNotFoundException e1) {
            // handle the exception
}

    El objetivo de la operación de la línea 3 es cargar el controlador JDBC de la base de datos en la memoria. Esta operación solo es necesario realizarla una vez. Sin embargo, repetirla no provoca ningún error. La clase del controlador JDBC se busca en la ruta de clases del proyecto. Por lo tanto, en el proyecto de Eclipse, el archivo [jar] que contiene la clase del controlador JDBC debe haberse incluido en la ruta de clases del proyecto.

    Una vez establecida la conexión, se pueden ejecutar comandos SQL. La forma en que se gestionan los comandos de lectura [SELECT] difiere de la utilizada para las operaciones de actualización [UPDATE, INSERT, DELETE]. Comenzaremos con los comandos SQL [SELECT]:

    • Líneas 8, 10: apertura de una transacción (línea 8) en modo de solo lectura (línea 10). Una transacción es una secuencia de sentencias SQL que o bien se ejecutan todas correctamente o bien fallan todas. Por lo tanto, en una transacción que contenga N sentencias SQL, si la (I+1)-ésima sentencia falla, las I sentencias anteriores se revertirán. Para una operación de lectura, no es necesaria una transacción. Sin embargo, crear una transacción de solo lectura puede permitir que ciertos SGBD realicen ciertas optimizaciones;
    • Línea 12: uso de un [PreparedStatement]. Un [PreparedStatement] suele tener parámetros indicados por el carácter ?. En este caso, no tiene ninguno. Un [PreparedStatement] es una instrucción preparada por el SGBD. Esta preparación tiene un coste y se realiza una sola vez. A continuación, el SGBD ejecuta esta instrucción preparada con los parámetros reales que sustituyen a los parámetros de marcador de posición ?. Tenga en cuenta que es preferible especificar las columnas deseadas en lugar de utilizar la notación * para recuperar todas las columnas. Al especificar los nombres de las columnas, sus valores se pueden recuperar en función de su posición en la instrucción SELECT;
    • Línea 13: ejecución del [PreparedStatement]. Se recupera un objeto [ResultSet];

    Un objeto [ResultSet] representa una tabla, es decir, un conjunto de filas y columnas. En un momento dado, solo tenemos acceso a una fila de la tabla, denominada fila actual. Cuando se crea inicialmente el [ResultSet], no hay ninguna fila actual. Debemos realizar una operación [ResultSet.next()] para obtenerla. La firma del método next es la siguiente:

        boolean next()

    Este método intenta pasar a la siguiente fila del [ResultSet] y devuelve true si tiene éxito, false en caso contrario. Si tiene éxito, la siguiente fila se convierte en la nueva fila actual. La fila anterior se pierde y no se puede recuperar.

    La tabla [ResultSet] tiene columnas denominadas labelCol1, labelCol2, ... tal y como se especifica en la consulta [SELECT] ejecutada. Con la consulta:

    SELECT ID as myId, NOM as myNom, CATEGORIE as myCategorie, PRIX as myPrix, DESCRIPTION as myDescription FROM PRODUITS
    • la columna [ID] se colocará en una columna del [ResultSet] denominada [myId];
    • la columna [NAME] se asignará a una columna del [ResultSet] denominada [myName];
    • ...

    En el ejemplo anterior, los identificadores [myCol] se denominan etiquetas de columna. Sin estas etiquetas, los nombres de las columnas del [ResultSet] dependen del SGBD. Cuando la instrucción [SELECT] opera sobre una sola tabla, las etiquetas de columna serán, por defecto, los nombres de las columnas solicitadas por la instrucción SELECT. El problema surge cuando la instrucción [SELECT] opera sobre varias tablas y estas contienen nombres de columna idénticos, como en el siguiente ejemplo:

    SELECT PRODUITS.NOM, CATEGORIES.NOM FROM PRODUITS, CATEGORIES WHERE PRODUITS.CATEGORIE_ID=CATEGORIES.ID

    suponiendo que la tabla [PRODUCTS] tiene una clave externa a la tabla [CATEGORIES] representada por la relación [PRODUCTS].CATEGORY_ID --> [CATEGORIES].ID, y que tanto la tabla [PRODUCTS] como la [CATEGORIES] tienen un campo [NAME]. En este caso, los nombres asignados en el [ResultSet] a las columnas [PRODUITS.NOM] y [CATEGORIES.NOM] dependen del SGBD. Para garantizar la portabilidad entre SGBD, aquí deben utilizarse las etiquetas de las columnas, por lo que escribiríamos:

    
SELECT PRODUITS.NOM as p_NOM, CATEGORIES.NOM as c_NOM FROM PRODUITS, CATEGORIES WHERE PRODUITS.CATEGORIE_ID=CATEGORIES.ID

    Para acceder a los distintos campos de la fila actual en el [ResultSet], se dispone de los siguientes métodos:

    Type getType("labelColi")

    para recuperar la columna denominada «labelColi» de la fila actual, es decir, la columna de la instrucción [SELECT] con esa etiqueta. Type hace referencia al tipo de datos del campo «labelColi». Se pueden utilizar los siguientes métodos [getType]: getInt, getLong, getString, getDouble, getFloat, getDate, ... En lugar de utilizar el nombre de la columna, puede utilizar su posición en la consulta [SELECT] ejecutada:

    Type getType(i)

    donde i es el índice de la columna deseada (i>=1).

    3.2.4. Paso 3: ejecución de sentencias SQL [INSERT, UPDATE, DELETE]

    Las sentencias SQL [INSERT, UPDATE, DELETE] son operaciones de actualización: modifican la base de datos, pero no devuelven ninguna fila. La única información que se devuelve es el número de filas afectadas por la operación de actualización.

    El código

    
Connection connexion = null;
        PreparedStatement ps = null;
        try {
            // ouverture connexion
            connexion = DriverManager.getConnection(url, user, passwd);
            // début transaction
            connexion.setAutoCommit(false);
            // en mode lecture / écriture
            connexion.setReadOnly(false);
            // on met à jour la table
            ps = connexion.prepareStatement("UPDATE PRODUITS SET PRIX=PRIX*1.1 WHERE CATEGORIE=?");
            // catégorie 1
            ps.setInt(1, 10);
            // exécution
            int nbLignes=ps.executeUpdate();
            // commit transaction
            connexion.commit();
        } catch (SQLException e1) {
            // on traite l'exception
            doCatchException(connexion, e1);
        } finally {
            // on traite le finally
            doFinally(null, ps, connexion);
        }
    }
    • línea 9: la conexión se utiliza para leer y escribir;
    • línea 11: un [PreparedStatement] con 1 parámetro (representado por ?). Puede haber varios parámetros. Se numeran a partir del 1;
    • línea 13: se asigna su valor al único parámetro. El primer parámetro de [setType] es la posición del parámetro en el [PreparedStatement] (1, 2, ...) y el segundo es el valor que se le asigna. Se pueden utilizar los métodos [setInt, setLong, setFloat, setDouble, setString, setDate, ...];
    • línea 15: se utiliza el método [executeUpdate], no [executeQuery], que está reservado para sentencias SELECT. El método devuelve el número de filas afectadas por la operación. Puede ser 0.
    • línea 17: se confirma la transacción;

    3.2.5. Paso 4: Cierre de la conexión

    En un entorno multiusuario, una conexión debe cerrarse lo antes posible, ya que un SGBD acepta un número limitado de conexiones abiertas. En los ejemplos anteriores, se cerró en la cláusula [finally] de las operaciones SQL, de modo que se cerrara independientemente de si se producía una excepción o no.

    3.3.5. La [UncheckedException]

      

    Consideremos la siguiente arquitectura:

    • la capa [JDBC] lanza excepciones [SQLException]. Esta excepción debe propagarse a través de las capas hasta llegar a la capa más alta, en este caso la capa de pruebas;

    La capa [DAO] podría simplemente dejar que la [SQLException] se propagara hasta la capa de pruebas. Pero dado que esta excepción no está controlada (deriva directamente de [Exception]), esto implicaría que la interfaz [IDao] de la capa [DAO] sería la siguiente:

    
public interface IDao {
 
    // ajouter des produits
    public List<Produit> addProduits(List<Produit> produits) throws SQLException;
 
    // liste de tous les produits
    public List<Produit> getAllProduits() throws SQLException;
 
    // un produit particulier
    public Produit getProduitById(int id) throws SQLException;
 
    public Produit getProduitByName(String name) throws SQLException;
 
    // mise à jour de plusieurs produits
    public int updateProduits(List<Produit> produits) throws SQLException;
 
    // suppression de tous les produits
    public int deleteAllProduits() throws SQLException;
 
    // suppression de plusieurs produits
    public int deleteProduits(int[] ids) throws SQLException;
}

    Y eso es muy molesto porque nos impide implementar la interfaz [IDao] con una clase que lanzaría una excepción diferente. Para solucionar este problema, la capa [DAO] lanzará una [DaoException] no controlada (derivada de [RuntimeException]), lo que nos permite omitir la cláusula [throws] en las firmas de los métodos de la interfaz. Como resultado, la interfaz puede ser implementada por cualquier clase que también lance una excepción no controlada, que puede ser diferente de la [DaoException].     El método [delete] utiliza transacciones. Una transacción permite agrupar sentencias SQL que deben completarse con éxito o revertirse en su totalidad. Hay cuatro operaciones que hay que tener en cuenta:

    • inicio de una transacción: [connection.setAutoCommit(false)];
    • fin de una transacción correcta: [connection.commit()]. En este caso, se confirman todas las operaciones realizadas en la base de datos durante la transacción;
    • fin de una transacción fallida: [connection.rollback()]. En este caso, se revierten todas las operaciones realizadas en la base de datos durante la transacción;

                try (ResultSet rs = ps.executeQuery()) {
                    while (rs.next()) {
                        produits.add(new Produit(rs.getInt(1), rs.getString(2), rs.getInt(3), rs.getDouble(4), rs.getString(5)));
                    }
                }
                // end transaction
                connexion.commit();
                // return to default mode
                connexion.setAutoCommit(true);
            } catch (SQLException e1) {
                // cancel the transaction
                daoException = doRollback(connexion, e1, 111);
            }
        } catch (SQLException e2) {
            // we handle the exception
            if (daoException == null) {
                daoException = new DaoException(112, e2, simpleClassName);
            }
        }
        // exception?
        if (daoException != null) {
            throw daoException;
        }
        // result
        return produits;
}
    • Línea 7: bloque try con el recurso [Connection]. La línea 27 garantiza que se cierre;
    • línea 13: bloque «try» con el recurso [PreparedStatement]. La línea 23 garantiza que se cierre;
    • línea 14: bloque try con el recurso [ResultSet]. La línea 19 garantiza que se cierre;
    • Línea 25: La transacción se revierte de la siguiente manera: 
    
    private DaoException doRollback(Connection connexion, Throwable e1, int code) {
        try {
            if (connexion != null) {
                connexion.rollback();
            }
        } catch (SQLException e) {
            e.printStackTrace();
        }
        // génération de l'exception
        return new DaoException(code, e1, simpleClassName);
}

    portée <T> type_résultat m(... , T value1, ...){
...

    type_résultat r=c.<T1>m(..., T1 value1, ..) ;

    donde T1 es el tipo real que sustituirá al tipo formal T del método m. La mayoría de las veces, el compilador es capaz de inferir el tipo T1 a partir de los argumentos del método m. Por lo tanto, la instrucción anterior se simplificará con frecuencia a:

    type_résultat r=c.m(..., T1 value1, ..) ;
