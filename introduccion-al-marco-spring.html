    2. Introducción al marco Spring

    Spring apareció por primera vez en 2004 como un contenedor de objetos. Desde entonces, ha evolucionado en múltiples ramas: Spring MVC, Spring Data, Spring Batch, ... [http://spring.io]. En este capítulo, nos centraremos exclusivamente en el contenedor de objetos. A continuación se presentan algunos puntos clave:

    • Una aplicación tiene múltiples clases, y algunas de ellas comparten objetos que deben ser únicos (singletons). Spring crea y gestiona estos singletons;
    • Spring coloca estos singletons en una estructura denominada contexto;
    • las clases acceden a los singletons de la aplicación solicitándolos a Spring mediante su nombre, tipo o ambos;
    • Spring crea los singletons y gestiona cualquier dependencia que puedan tener: un singleton puede, de hecho, tener referencias a uno o más singletons. Cuando Spring crea un singleton, también crea sus dependencias;
    • Cuando se inicia una aplicación basada en Spring, puede solicitar a Spring que cree todos los singletons de la aplicación. Estos estarán entonces disponibles en el contexto de Spring;
    • Spring facilita el uso de arquitecturas por capas y la programación basada en interfaces. En los casos más sencillos, cada capa está implementada por un singleton y implementa una interfaz. Si la aplicación trabaja con las interfaces de las capas en lugar de con sus clases de implementación, se obtiene una arquitectura escalable que permite cambiar la implementación de una capa sin afectar a las demás, gracias a las dos características siguientes:
      • la aplicación obtiene una referencia a la capa a través de su nombre. Spring le proporciona una referencia a la clase que implementa la capa;
      • la aplicación utiliza esta referencia como la de la interfaz de la capa y no como la de una clase;

    Los singletons se pueden declarar de tres formas, que se pueden combinar:

    • dentro de un archivo XML,
    • en una clase de configuración especial;
    • con cualquier clase mediante anotaciones;

    A continuación, presentamos tres ejemplos de configuración:

    • [ejemplo-01]: configuración centralizada en un único archivo XML;
    • [ejemplo-02]: configuración centralizada en una única clase Java;
    • [ejemplo-03]: configuración distribuida en varias clases Java;

    El último ejemplo [ejemplo-04] se centra en la configuración de Spring de una arquitectura en capas. Este es el ejemplo más importante. Se utilizará de forma sistemática para configurar las arquitecturas de este documento.

    Estos cuatro ejemplos sientan las bases para lo que viene a continuación:

    • Configuración de Spring e inyección de dependencias;
    • el uso de Maven para gestionar las dependencias de un proyecto;
    • uso de JUnit para probar proyectos;

package istia.st.spring.core;
 
public class Personne {
 
    // fields
    private String nom;
    private String prenom;
    private int age;
 
    // manufacturers
    public Personne() {
 
    }

        this.nom = nom;
        this.prenom = prénom;
        this.age = âge;

    // toString

    }
 
    // getters and setters

    public String getNom() {
        return nom;
    }
 
    public void setNom(String nom) {
        this.nom = nom;
    }
 
    public String getPrenom() {
        return prenom;
    }
 
    public void setPrenom(String prenom) {
        this.prenom = prenom;
    }
 
    public int getAge() {
        return age;
    }
 
    public void setAge(int age) {
        this.age = age;
    }
 
}

    2.2.4. El archivo de configuración de Spring

     
    
<?xml version="1.0" encoding="UTF-8"?>
<beans xmlns="http://www.springframework.org/schema/beans" xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance" xmlns:util="http://www.springframework.org/schema/util"
    xsi:schemaLocation="http://www.springframework.org/schema/beans http://www.springframework.org/schema/beans/spring-beans-4.0.xsd
        http://www.springframework.org/schema/util http://www.springframework.org/schema/util/spring-util-4.0.xsd">
    <!-- Person 01 -->
    <bean id="personne_01" class="istia.st.spring.core.Personne">
        <constructor-arg index="0" value="dubois" />
        <constructor-arg index="1" value="paul" />
        <constructor-arg index="2" value="34" />
    </bean>
    <!-- Person 02 -->
    <bean id="personne_02" class="istia.st.spring.core.Personne">
        <property name="nom" value="martin" />
        <property name="prenom" value="micheline" />
        <property name="age" value="18" />
    </bean>
    <!-- a list of people -->
    <util:list id="club">
        <ref bean="personne_01" />
        <ref bean="personne_02" />
    </util:list>
    <!-- an apartment -->
    <bean id="appartement" class="istia.st.spring.core.Appartement">
        <property name="surface" value="100" />
        <property name="proprietaire" ref="personne_01" />
    </bean>
</beans>
    • líneas 2 y 27: los singletons se definen dentro de una etiqueta <beans>;
    • líneas 6–10: cada singleton se define mediante una etiqueta <bean>;
    • línea 6: [id] es el identificador del singleton. [class] es el nombre completo de la clase que se va a instanciar;
    • líneas 7–9: los tres valores que se pasan al constructor de la clase [Person];
    • líneas 12-16: la clase [Person] se crea primero utilizando su constructor por defecto [new Person()]. A continuación, para cada etiqueta [property], se utiliza un método setter de la clase. Por ejemplo, en la línea 13, se ejecutará el método [setName("martin")]. Por lo tanto, el método [setName] debe existir. Este es un punto importante que hay que recordar;
    • líneas 18-21: la etiqueta <util:list> se utiliza para definir un singleton que es una lista;
    • línea 19: hace referencia al singleton [person_01] definido en la línea 6. Esto es lo que se conoce como inyección de dependencias. Se pueden utilizar dos atributos para inicializar el campo de un singleton:
      • [value]: para asignar un valor primitivo (cadena, número, fecha, etc.) al campo,
      • [ref]: para asignar la referencia de un objeto Spring al campo;

    2.2.5. La clase ejecutable

     
    
package istia.st.spring.core;
 
import java.util.ArrayList;
import java.util.List;
 
import org.springframework.context.ApplicationContext;
import org.springframework.context.support.ClassPathXmlApplicationContext;
 
public class Demo01 {
 
    @SuppressWarnings({ "unchecked", "resource" })
    public static void main(String[] args) {
        // spring context retrieval
        ApplicationContext ctx = new ClassPathXmlApplicationContext("config-01.xml");
        // beans are recovered
        Personne p01 = ctx.getBean("personne_01", Personne.class);
        Personne p02 = ctx.getBean("personne_02", Personne.class);
        List<Personne> club = ctx.getBean("club", new ArrayList<Personne>().getClass());
        Appartement appart01 = ctx.getBean(Appartement.class);
        // we display them
        System.out.println("personnes--------");
        System.out.println(p01);
        System.out.println(p02);
        System.out.println("club--------");
        for (Personne p : club) {
            System.out.println(p);
        }
        System.out.println("appartement--------");
        System.out.println(appart01);
        // recovered beans are singletons
        // they can be requested several times, but the same bean is always retrieved
        Personne p01b = ctx.getBean("personne_01", Personne.class);
        System.out.println(String.format("beans [p01,p01b] identiques ? %s", p01b == p01));
    }
}
    • línea 14: crea el contexto Spring. A continuación, se instancian todos los singletons definidos en el archivo [config-01.xml];
    • línea 16: solicita una referencia al singleton identificado por [person_01] de tipo [Person]. Este segundo parámetro es opcional, pero si se omite, se devuelve una referencia de tipo [Object], que luego debe ser convertida al tipo [Person];
    • línea 19: no utilizamos el nombre del bean, sino solo su tipo, ya que solo hay un singleton de tipo [Apartment];
    • línea 18: se utilizan tanto el identificador como el tipo del singleton deseado. El identificador es redundante, ya que solo hay un singleton de tipo [new ArrayList<Person>().getClass()];
    • Líneas 32–33: muestran que si solicitamos el mismo singleton varias veces, siempre obtenemos la misma referencia, lo que demuestra que efectivamente estamos ante un singleton. Es importante comprender este punto;

    Nota: Se puede generar una clase ejecutable de la siguiente manera [1-6]:

    • Al marcar [6] se garantiza que la clase generada contenga un método estático [main], lo que la hace ejecutable;

    2.2.6. Dependencias del proyecto

     
    • Dependencias de Spring: [spring-core, spring-beans, spring-context, spring-expression, commons-logging];

    Las dependencias se añaden al proyecto de la siguiente manera:

    • en [1]: haz clic con el botón derecho del ratón en el proyecto / [Ruta de compilación] / [Configurar ruta de compilación];
    • en [2]: [Añadir JAR] si los JAR que se van a añadir se encuentran en una carpeta del proyecto. De lo contrario, [Añadir JAR externos];
    • en [3], selecciona los archivos JAR que deseas añadir a la ruta de clases (ClassPath) del proyecto (en este caso, se encuentran en la carpeta [lib] del proyecto);

    Definición: El [ClassPath] de un proyecto es el conjunto de directorios que la JVM (Máquina Virtual Java) que ejecuta el proyecto busca para encontrar una clase a la que hace referencia el proyecto. En el caso de un proyecto de Eclipse, el [ClassPath] consta de lo siguiente:

    • la carpeta [bin] del proyecto;
    • los elementos de la [Build Path] del proyecto;

    La carpeta [bin] es la carpeta resultante de la compilación de la carpeta [src]. Por lo tanto, todo lo que se coloque en la carpeta [src] forma parte automáticamente de la [ClassPath] (aunque no sea un archivo .java). Así, en el proyecto anterior, el archivo de configuración de Spring [config-01.xml], que se encuentra en la carpeta [src], formará parte de la [ClassPath] del proyecto en tiempo de ejecución.

    2.3.1. El proyecto Eclipse

     

    2.3.2. La clase de configuración de Spring

    
package istia.st.spring.core;
 
import java.util.ArrayList;
import java.util.List;
 
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
 
@Configuration
public class Config {
 
    @Bean
    public Personne personne_01() {
        return new Personne("Paul", "Dubois", 34);
    }
 
    @Bean
    public Personne personne_02() {
        return new Personne("Martin", "Micheline", 18);
    }
 
    @Bean
    public List<Personne> club(Personne personne_01, Personne personne_02) {
        List<Personne> personnes = new ArrayList<Personne>();
        personnes.add(personne_01);
        personnes.add(personne_02);
        return personnes;
    }
 
    @Bean
    public Appartement appartement(Personne personne_01) {
        Appartement appartement = new Appartement();
        appartement.setSurface(200);
        appartement.setPropriétaire(personne_01);
        return appartement;
    }
}
    • línea 9: la anotación [@Configuration] es una anotación de Spring. Indica que la clase anotada define singletons. Estos se definen mediante la anotación [@Bean]. Spring ejecutará todos los métodos anotados con [@Bean]. Estos crean los singletons de la aplicación;
    • líneas 12–15: definen un singleton identificado por [person_01], es decir, el nombre del método.
    • línea 23: los parámetros [person_01, person_02] llevan los nombres de singletons. Spring los inicializará automáticamente con las referencias de dichos singletons. A esto se le denomina «inyección de parámetros»;

    Esta forma de configurar singletons es más explícita que la que utiliza el archivo XML. De hecho, estamos reproduciendo nosotros mismos lo que Spring hacía implícitamente basándose en el archivo XML.

    Gestionar manualmente las dependencias de un proyecto se convierte en un quebradero de cabeza cuando se utilizan bibliotecas Java cuyas dependencias se desconocen. Por ejemplo, el marco [Hibernate], que gestiona el acceso a bases de datos, tiene docenas de dependencias. El proyecto [Maven] resuelve este problema. Usted especifica l encia que necesita. Se busca automáticamente esa dependencia en los repositorios de Maven distribuidos por Internet. Si l encia solicitada tiene sus propias dependencias, estas también se descargan automáticamente. Estas dependencias descargadas se almacenan en un repositorio local en el equipo. Si más adelante otra aplicación necesita la misma dependencia, no se descargará, sino que se recuperará del repositorio local. Una dependencia se caracteriza por los siguientes elementos:

    • línea 17: una etiqueta <dependency>;
    • línea 18: un atributo [groupId] que, por lo general, identifica a la empresa que creó la dependencia;
    • línea 19: un atributo [artifactId] que identifica la dependencia;
    • línea 20: un atributo [version] que identifica la versión deseada;

    La generación del proyecto producirá por sí misma un componente Maven definido por las líneas 4–8:

    • líneas 4-6: los atributos [groupId, artifactId, version] que acabamos de describir;
    • líneas 7-8: son atributos opcionales;

    Volveremos al papel de las líneas 24–40 un poco más adelante. Para convertir un proyecto estándar de Eclipse en un proyecto Maven, hay que hacer dos cosas:

    • crear el archivo [pom.xml] que se muestra arriba;
    • declarar que el proyecto es ahora un proyecto Maven [1-4]:

    El icono de un proyecto Maven incluye una M [4]. La S indica que el proyecto contiene componentes Spring. No se recomienda convertir (como acabamos de hacer) un proyecto Eclipse en un proyecto Maven, ya que el proyecto carecerá entonces de la estructura esperada para un proyecto Maven, lo que en ocasiones puede provocar problemas inesperados.

@RunWith(SpringJUnit4ClassRunner.class)
public class JUnitTest {

    @Qualifier("ui1")

    @Qualifier("ui2")
    private IUi ui2;

    @Qualifier("metier2")
    private IMetier metier2;

    @Qualifier("dao2")
    private IDao dao2;

    public void testDao() {
        Assert.assertEquals(30, dao1.doSomethingInDaoLayer(10, 20));
        Assert.assertEquals(-10, dao2.doSomethingInDaoLayer(10, 20));
    }

    @Test
    public void testMetier() {

    • línea 34: la anotación [@Test] designa un método que se ejecutará durante las pruebas. Otras anotaciones posibles son las siguientes:

      • [@AfterClass]: método que se ejecutará una vez que todas las pruebas hayan finalizado;
      • [@Before]: método que se ejecutará antes de cada prueba;
      • [@After]: método que se ejecutará después de cada prueba;

    Las aserciones que se pueden utilizar en un método de prueba son las siguientes:

    • assertEquals(expresión1, expresión2): comprueba que los valores de las dos expresiones sean iguales. Se aceptan muchos tipos de expresiones (int, String, float, double, boolean, char, short). Si las dos expresiones no son iguales, se lanza una excepción de tipo [AssertionFailedError],
    • assertEquals(real1, real2, delta): comprueba que dos números reales sean iguales con un margen de delta, es decir, abs(real1-real2) <= delta. Por ejemplo, se podría escribir assertEquals(real1, real2, 1E-6) para verificar que dos valores sean iguales con un margen de 10⁻⁶,
    • assertEquals(message, expression1, expression2) y assertEquals(message, real1, real2, delta) son variantes que permiten especificar el mensaje de error que se asociará a la excepción [AssertionFailedError] lanzada cuando falla el método [assertEquals],
    • assertNotNull(Object) y assertNotNull(message, Object): comprueba que la referencia a Object no sea nula,
    • assertNull(Object) y assertNull(message, Object): comprueba que la referencia a Object sea nula,
    • assertSame(Object1, Object2) y assertSame(message, Object1, Object2): comprueba que las referencias Object1 y Object2 apuntan al mismo objeto,
    • assertNotSame(Object1, Object2) y assertNotSame(message, Object1, Object2): comprueba que las referencias Object1 y Object2 no apuntan al mismo objeto;

Puedes optar por utilizar la implementación [Ui1, Metier1, Dao1] o [Ui2, Metier2, Dao2] simplemente configurándola. Así, en la prueba JUnit anterior, si se mantiene únicamente la inyección de los beans [ui1, metier1, dao1], se está trabajando con la primera arquitectura. Para cambiar la arquitectura, basta con cambiar los beans inyectados. Esto se hace sin modificar el código de las capas que implementan las interfaces. Este tipo de programación se denomina programación basada en interfaces porque no utilizamos las instancias de las clases que implementan las capas, sino las instancias de sus interfaces.

    2.6. Conclusión

    • Spring gestiona objetos que son singletons (una única instancia). Spring también gestiona objetos que se instancian cada vez que se solicita una instancia a Spring. Este caso también se presentará en este documento;
    • estos objetos pueden declararse de diversas formas que pueden combinarse:
      • en un archivo XML,
      • en una clase Java anotada con [@Configuration],
      • con cualquier clase Java anotada con [@Component, @Service, ...];
    • un objeto Spring puede inyectarse en otro objeto Spring utilizando la anotación [@Autowired]. Esto se conoce como inyección de dependencias (DI);
    • Spring resulta muy útil para configurar arquitecturas en capas cuando se utiliza junto con el paradigma de programación basado en interfaces;
