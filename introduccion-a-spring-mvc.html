    16. Introducción a Spring MVC

    16.1. El papel de Spring MVC en una aplicación web

    Situemos Spring MVC en el contexto del desarrollo de una aplicación web. En la mayoría de los casos, se basará en una arquitectura de varios niveles como la siguiente:

    • la capa [Web] es la que interactúa con el usuario de la aplicación web. El usuario interactúa con la aplicación web a través de páginas web que se muestran en un navegador. Spring MVC reside en esta capa y solo en ella;
    • la capa [de negocio] implementa la lógica de negocio de la aplicación, como el cálculo de un salario o una factura. Esta capa utiliza datos del usuario a través de la capa [Web] y del SGBD a través de la capa [DAO];
    • la capa [DAO] (objetos de acceso a datos), la capa [ORM] (mapeador relacional de objetos) y el controlador JDBC gestionan el acceso a los datos en el SGBD. La capa [ORM] actúa como puente entre los objetos gestionados por la capa [DAO] y las filas y columnas de las tablas de una base de datos relacional. Una especificación denominada JPA (Java Persistence API) permite abstraerse del ORM utilizado si este implementa dichas especificaciones. Este será el caso en este tutorial, por lo que a partir de ahora nos referiremos a la capa ORM como la capa JPA;
    • La integración de estas capas la gestiona el marco Spring;

    16.2. El modelo de desarrollo de Spring MVC

    Spring MVC implementa el patrón arquitectónico MVC (Modelo-Vista-Controlador) de la siguiente manera:

    El procesamiento de una solicitud de un cliente se lleva a cabo de la siguiente manera:

    1. solicitud: las URL solicitadas tienen el formato http://machine:port/contexte/Action/param1/param2/....?p1=v1&p2=v2&... El [controlador frontal] utiliza un archivo de configuración o anotaciones Java para «enrutar» la solicitud al controlador correcto y a la acción correcta dentro de ese controlador. Para ello, utiliza el campo [Action] de la URL. El resto de la URL [/param1/param2/...] consta de parámetros opcionales que se pasarán a la acción. La «C» de MVC se refiere aquí a la cadena [Front Controller, Controller, Action]. Si ningún controlador puede gestionar la acción solicitada, el servidor web responderá que no se ha encontrado la URL solicitada.
    1. Procesamiento
        • (continuación)
      • La acción seleccionada puede utilizar los parámetros que le ha pasado el [controlador frontal]. Estos pueden provenir de varias fuentes:
        • la ruta [/param1/param2/...] de la URL,
        • los parámetros [p1=v1&p2=v2] de la URL,
        • de los parámetros enviados por el navegador con su solicitud;
      • Al procesar la solicitud del usuario, la acción puede necesitar la capa [business] [2b]. Una vez procesada la solicitud del cliente, puede desencadenar diversas respuestas. Un ejemplo clásico es:
        • una página de error si la solicitud no se ha podido procesar correctamente
        • una página de confirmación en caso contrario
      • La acción indica a una vista específica que se renderice [3]. Esta vista mostrará los datos conocidos como el modelo de vista. Esta es la «M» de MVC. La acción creará este modelo de vista [2c] e indicará a una vista que se renderice [3];
    1. Respuesta: la vista seleccionada V utiliza el modelo M creado por la acción para inicializar las partes dinámicas de la respuesta HTML que debe enviar al cliente y, a continuación, envía esta respuesta.

    En el caso de un servicio web / JSON, la arquitectura anterior se modifica ligeramente:

    • en [4a], el modelo, que es una clase Java, se convierte en una cadena JSON mediante una biblioteca JSON;
    • en [4b], esta cadena JSON se envía al navegador;

    Ahora, aclaremos la relación entre la arquitectura web MVC y la arquitectura por capas. Dependiendo de cómo se defina el modelo, estos dos conceptos pueden estar relacionados o no. Consideremos una aplicación web Spring MVC de una sola capa:

    Si implementamos la capa [Web] con Spring MVC, tendremos efectivamente una arquitectura web MVC, pero no una arquitectura en capas. En este caso, la capa [Web] se encargará de todo: la presentación, la lógica de negocio y el acceso a los datos. Son las acciones las que realizarán este trabajo.

    Ahora, consideremos una arquitectura web multicapa:

    La capa [Web] se puede implementar sin un marco de trabajo y sin seguir el modelo MVC. En ese caso, tenemos una arquitectura de varias capas, pero la capa Web no implementa el modelo MVC.

    Por ejemplo, en el entorno .NET, la capa [Web] anterior se puede implementar con ASP.NET MVC, lo que da como resultado una arquitectura en capas con una capa [Web] de estilo MVC. Una vez hecho esto, podemos sustituir esta capa ASP.NET MVC por una capa ASP.NET clásica (WebForms) sin modificar el resto (lógica de negocio, DAO, ORM). De este modo, obtenemos una arquitectura en capas con una capa [Web] que ya no se basa en MVC.

    En MVC, dijimos que el modelo M era el de la vista V, es decir, el conjunto de datos mostrados por la vista V. Se ofrece otra definición del modelo M en MVC:

    Muchos autores consideran que lo que se encuentra a la derecha de la capa [Web] constituye el modelo M de MVC. Para evitar ambigüedades, podemos referirnos a:

    • el modelo de dominio cuando nos refiramos a todo lo que se encuentra a la derecha de la capa [Web]
    • el modelo de vista cuando nos refiramos a los datos mostrados por una vista V

    En lo sucesivo, el término «modelo M» se referirá exclusivamente al modelo de una vista V.

    16.3.3. La arquitectura de un servicio Spring [web / JSON]

    Para un servicio web/JSON, Spring MVC implementa el modelo MVC de la siguiente manera:

    • En [4a], el modelo —que es una clase Java— se convierte en una cadena JSON mediante una biblioteca JSON;
    • en [4b], esta cadena JSON se envía al navegador;

    16.3.4. El controlador C

      

    La aplicación importada tiene el siguiente controlador:

    
package hello;
 
import java.util.concurrent.atomic.AtomicLong;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.RestController;
 
@RestController
public class GreetingController {
 
    private static final String template = "Hello, %s!";
    private final AtomicLong counter = new AtomicLong();
 
    @RequestMapping("/greeting")
    public Greeting greeting(@RequestParam(value = "name", defaultValue = "World") String name) {
        return new Greeting(counter.incrementAndGet(), String.format(template, name));
    }
}
    • Línea 9: La anotación [@RestController] convierte a la clase [GreetingController] en un controlador Spring, lo que significa que sus métodos se registran para gestionar URL. Ya hemos visto la anotación similar [@Controller]. El tipo de retorno de los métodos de ese controlador era [String], que era el nombre de la vista que se iba a mostrar. Aquí es diferente. Los métodos de un [@RestController] devuelven objetos que se serializan para enviarse al navegador. El tipo de serialización que se realiza depende de la configuración de Spring MVC. Aquí, se serializarán a JSON. Es la presencia de una biblioteca JSON en las dependencias del proyecto lo que hace que Spring Boot configure automáticamente el proyecto de esta manera;
    • línea 14: la anotación [@RequestMapping] especifica la URL gestionada por el método, en este caso la URL [/greeting];
    • línea 15: ya hemos explicado la anotación [@RequestParam]. El resultado devuelto por el método es un objeto de tipo [Greeting].
    • línea 12: un entero largo de tipo atómico. Esto significa que admite el acceso concurrente. Es posible que varios subprocesos quieran incrementar la variable [counter] al mismo tiempo. Esto se gestionará correctamente. Un subproceso solo puede leer el valor del contador una vez que el subproceso que lo está modificando haya finalizado su modificación.

    16.3.5. El modelo M

    El modelo M generado por el método anterior es el siguiente objeto [Greeting]:

      
    
package hello;
 
public class Greeting {
 
    private final long id;
    private final String content;
 
    public Greeting(long id, String content) {
        this.id = id;
        this.content = content;
    }
 
    public long getId() {
        return id;
    }
 
    public String getContent() {
        return content;
    }
}

    La transformación JSON de este objeto creará la cadena {"id":n,"content":"text"}. En definitiva, la cadena JSON generada por el método del controlador tendrá el siguiente formato:

    {"id":2,"content":"Hello, World!"}

    o 

    {"id":2,"content":"Hello, John!"}
